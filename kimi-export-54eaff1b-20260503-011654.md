<details><summary>Thinking</summary>

`void instance.connect()` — без try-catch. Если `connect()` выбросит синхронно (например, `new WebSocket("invalid")`), ошибка всплывёт в React.

Но `new WebSocket("")` не выбросит синхронно — он просто создаст объект WebSocket с relative URL. Ошибка произойдёт асинхронно (через `onerror`).

Так что `url=""` безопасен с точки зрения синхронных ошибок. WebSocket просто будет пытаться подключиться к текущему origin и получать `onerror`.

Может быть, это приемлемо? System contour редко используется, и один неудачный WebSocket не критичен.

Но есть лучший вариант. Давайте посмотрим, что происходит, если мы передадим `resolveUrl` вместо `url`:

```tsx
<WebSocketProvider
    resolveUrl={() => contour.wsUrl || "ws://localhost:0"}
    ...
>
```

`resolveUrl` — функция, которая возвращает URL. `WebSocketProvider` использует её в `useEffect`:
```javascript
const wsUrl = urlProp ?? resolveUrlRef.current();
```

Если `urlProp` = `undefined`, то `wsUrl = resolveUrlRef.current()`. Если `resolveUrl` возвращает `""`, то `wsUrl = ""`.

Но мы можем сделать так:
```javascript
const wsUrl = urlProp ?? resolveUrlRef.current();
```

Если `urlProp` = `undefined`, а `resolveUrl` возвращает `""`, `wsUrl` будет `""`. Но если `urlProp` = `""` (пустая строка), то `urlProp ?? resolveUrlRef.current()` вернёт `""`, потому что `??` не считает пустую строку `null`/`undefined`.

То есть если мы передаём `url=""`, `wsUrl` будет `""`.

Если мы НЕ передаём `url` (оставляем `undefined`), а `resolveUrl` возвращает `""`, то `wsUrl` тоже будет `""`.

Но мы можем сделать `resolveUrl` возвращающим `undefined`? Тогда `wsUrl = undefined`, и `new WebSocket(undefined)` = `new WebSocket("undefined")`? Нет, `undefined` преобразуется в строку `"undefined"`.

Хм... Может быть, мы можем передать `createClient`, который создаёт noop WebSocket?

```tsx
<WebSocketProvider
    url={contour.wsUrl || "ws://localhost:0"}
    createClient={() => ({ connect: () => Promise.resolve(), disconnect: () => {}, ... })}
>
```

   950	    if (this.wfmExecuteAdapter) return this.wfmExecuteAdapter;
   951	    const info = await this.getAdaptersInfo({});
   952	    let found: ExecuteAdapter | null = null;
   953	    const walk = (nodes: AdapterTreeNode[]) => {
   954	      for (const n of nodes) {
   955	        if (found) return;
   956	        if (n.type === "command" && n.data?.CommandName === "WFM.Execute") {
   957	          found = {
   958	            AdapterName: n.data.AdapterName,
   959	            Level: n.data.Level,
   960	            AdapterType: n.data.AdapterType,
   961	          };
   962	          return;
   963	        }
   964	        if (n.nodes) walk(n.nodes);
   965	      }
   966	    };
   967	    walk(info.Adapters ?? []);
   968	    if (!found) {
   969	      throw new Error("Command 'WFM.Execute' not found in adapters info.");
   970	    }
   971	    this.wfmExecuteAdapter = found;
   972	    return found;

## Bug Analysis: CRUD Editor Tab Switch After Record Update

### 1. Summary
The tab does **not** actually switch IDs, but its **label and metadata are corrupted** after an Update in `RecordDialog`. This happens because `CrudEditorPage.tsx` has a special-case block that merges the entire updated record payload into the active tab’s `model` object when the model is `CRUDModel`. Since `CRUDModel` records contain a `Name` field (the name of the model they define), the tab’s `model.Name` is overwritten, making the tab visually appear as if it changed to that model.

There is **no** `useCrudEditor` hook or `CrudEditorProvider` in the codebase. Tab state is managed **locally** inside `CrudEditorPage.tsx` via `useState`:

*Note: If the user later clicks the Refresh button, the request **will** actually use the corrupted `model.Name` (`"MyModel"`), because `loadModelData(activeTab)` will then read the already-corrupted state.*

## Резюме: почему таб «менял» модель после Update

### Корень проблемы

В `CrudEditorPage.tsx` после успешного Update был специальный блок (строки 157–161):

```tsx
// Если редактировали CRUDModel — обновить model в табе, чтобы Enums/Properties
// применились к другим открытым моделям без перезагрузки страницы.
if (model.Name === "CRUDModel" && overlay.type !== "delete") {
  updateTab(activeTab.id, { model: { ...model, ...data } as CrudModel });
}
```

**Что происходило:**
1. Пользователь открывал таб **CRUDModel** → `tab.model.Name === "CRUDModel"`.
2. Открывал запись (например, модели `MyModel`) в `RecordDialog`.
3. Нажимал **Update** → `handleSubmitRecord` получал `data` — это поля записи `MyModel`, включая `Name: "MyModel"`, `Properties`, `Enums` и т.д.
4. Блок выше делал `{ ...model, ...data }` — **spread всей записи поверх объекта модели таба**.
5. В результате `tab.model.Name` перезаписывалось с `"CRUDModel"` на `"MyModel"`.
6. В UI таб отображался уже как `MyModel` (потому что лейбл берётся из `tab.model.Name`), хотя `tab.id` оставался `"CRUDModel"`.
7. Следующий `loadModelData` или ручной Refresh начинал запрашивать данные уже для модели `"MyModel"` вместо `"CRUDModel"`.

### Почему этот блок был бесполезен

Каждый таб хранит **свою независимую копию** объекта `model`. Обновление `model` в одном табе никак не передаётся в другие открытые табы. То есть комментарий «применилось к другим открытым моделям» был неверен — блок ломал текущий таб, но не помогал другим.

### Фикс

Удалил этот блок целиком. Теперь после Update:
- Таб остаётся **CRUDModel**.
- Вызывается `loadModelData(activeTab)`, который перезагружает список записей для текущей модели.
- Никаких ложных смен модели в табе не происходит.

Build прошёл успешно (`tsc` + `vite build` ✅).
